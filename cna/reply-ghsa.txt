Recap:

  Endpoint: POST /llmchat/connect (ContextForge MCP Gateway, mcp-contextforge-gateway).
  Flaw: the URL is validated once (mcpgateway/routers/llmchat_router.py:1083-1087 in 1.1.1) but
  the streamable-HTTP transport resolves the hostname again
  (mcpgateway/services/mcp_client_chat_service.py:105) with no IP pinning. A TTL-0 name that
  answers public-then-127.0.0.1 passes validation and connects to loopback.
  Effect: an authenticated user with the default "developer" role gets the internal server's
  tool list from /llmchat/connect and invokes those tools via /llmchat/chat.
  Affected: 1.0.0-RC2 through 1.1.1 (rebinding). 0.9.0 and 1.0.0-BETA-1 through 1.0.0-RC1 had
  no URL validation at all (direct SSRF) and are worth separate IDs.
  Verified: 1.1.1 at commit 85474a7c0eefc8c5d0e958400af7bc0ce59dfe63, isolated lab, plus a
  variant using a real public model provider.
  Fix: the pinning helpers already used by DCR/A2A/tool services

  mcpgateway/common/validators.py:76,1651); /llmchat/connect never calls them.
