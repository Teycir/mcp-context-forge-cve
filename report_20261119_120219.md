## 1. Executive Summary

### 1.1 Background
Objective: prove that an authenticated low-privilege user (default `developer` role) can abuse `POST /llmchat/connect` to reach services bound to the gateway's loopback, bypassing the platform's SSRF protection. Prior PoC only listed tools with an admin account; this engagement re-verified with a non-admin role, a TTL-honoring caching resolver, and full tool-invocation/data-return proof, plus negative controls.

### 1.2 Overall Posture
The SSRF guard (`validate_url`) runs once at connect time and the hostname is resolved again later by the streamable-HTTP transport — a textbook TOCTOU. The codebase already ships pinning helpers (`pin_url_to_resolved_ip`, `validate_url_for_connection_pinning`, `resolve_pinned_target`) used by the A2A card import, tool service, DCR and completion paths, but **not** by `/llmchat/connect`. The defect is therefore systemic-but-localised: one endpoint skipped an existing mitigation.

The exploit requires only a DNS name the attacker controls and a resolver that honours TTL 0. No admin rights are needed at exploitation time; provider/model provisioning is normal configuration performed by a platform admin, and the default `developer` role already holds `llm.invoke`.

### 1.3 Risk Profile

| Rating | CVSS 3.1 | Count | Finding |
|---|---|---|---|
| High | 8.2 | 1 | RT-01 DNS-rebinding SSRF → internal MCP tool invocation |

Overall risk: **High**. Confidentiality impact is demonstrated (internal-only tool output returned to the user); integrity impact is plausible (any tool exposed by an internal MCP server is reachable, including write-capable tools).

### 1.4 Recommendation Summary
1. **RT-01 (now):** make `/llmchat/connect` use the existing pinning helpers — resolve once, validate, then pass the pinned IP to the transport (or disable transport-level re-resolution).
2. Defence in depth: re-validate at connect *and* per request inside the transport; deny RFC1918/loopback/link-local at socket-connect time, not only at URL parse time.
3. Restrict `llm.invoke` to roles that are explicitly trusted to reach internal networks, or require an admin-approved server allowlist.

## 4. Findings Detail

### RT-01 — DNS-Rebinding SSRF in `/llmchat/connect` allows invocation of internal-only MCP tools

- **Severity:** High
- **CVSS 3.1:** 8.2 — `AV:N/AC:H/PR:L/UI:N/S:C/C:H/I:H/A:N` — https://www.first.org/cvss/calculator/3.1#CVSS:3.1/AV:N/AC:H/PR:L/UI:N/S:C/C:H/I:H/A:N
- **CWE:** CWE-918 (Server-Side Request Forgery)
- **Affected URL/Area:** `POST /llmchat/connect` (and subsequent `POST /llmchat/chat`), `mcpgateway/routers/llmchat_router.py:1083-1087`, transport at `mcpgateway/services/mcp_client_chat_service.py:105`
- **Difficulty to exploit:** Medium (needs attacker-controlled DNS; no admin rights at exploit time)
- **Authentication required:** Yes — any user holding the default `developer` role (`llm.invoke`)
- **User interaction required:** No
- **Verified at (UTC):** 2026-11-19T12:45:40Z (connect), 2026-11-19T12:45:54Z (tool invocation)

#### Issue Description
`/llmchat/connect` validates the user-supplied `server.url` with `validate_url`, which resolves the hostname once and rejects private/loopback answers. The validated URL string is then handed to the streamable-HTTP MCP transport, which performs its **own** DNS resolution when it opens the connection. Nothing pins the IP that was validated to the IP that is dialled.

An attacker who controls a hostname can answer the first query with a public address (passing validation) and every subsequent query with `127.0.0.1`. The transport then connects to the gateway's loopback, where internal MCP servers may be listening, and `/llmchat/chat` invokes their tools on the attacker's behalf. The platform already contains the correct primitive (`pin_url_to_resolved_ip`, `validate_url_for_connection_pinning`, `resolve_pinned_target`) and uses it in several other import/connect paths; `/llmchat/connect` was simply not migrated.

#### Attack Scenario
1. Attacker registers `rebind.test` with an authoritative server that returns `93.184.216.34` on the first A query and `127.0.0.1` afterwards, TTL 0.
2. A platform admin (legitimate configuration) creates an `openai_compatible` provider whose `api_base` is `http://rebind.test:8081/v1`, plus a model `stub-model`. Validation queries the name once and sees the public address.
3. The attacker — a normal user with only the default `developer` role — calls `POST /llmchat/connect` with `server.url=http://rebind.test:19000/mcp`.
4. Validation resolves the first query to the public address; the transport resolves again, gets `127.0.0.1`, and connects to the internal MCP server bound to loopback.
5. `POST /llmchat/chat` causes the agent to call `internal_only_secret_tool_7f3a`; the tool's output (`INTERNAL_ONLY_TOOL_REACHED_7f3a`) is returned to the attacker in the chat response — proof of internal reach and data return.

#### Steps to Reproduce / PoC
Prerequisites: Linux host with Docker; Python 3.12; source checkout at `85474a7c`; `lab/` scripts from this engagement (`pocs/` copies).

3. Start the lab services (the script does this): authoritative DNS `10.77.0.3:5353` (control `:8082`), TTL cache `gw:127.0.0.1:53`, internal MCP `gw:127.0.0.1:19000`, OpenAI-compatible stub `gw:127.0.0.1:8081`, gateway `gw:0.0.0.0:4444`.
4. As platform admin, provision the normal configuration: create user `dev@example.com`, team `Lab Team`, assign the **team-scoped** `developer` role, create provider `stub` with `api_base=http://rebind.test:8081/v1`, create model `stub-model`.
5. Set the DNS policy to `public` and reset the counter, then verify the provider is accepted: `curl 'http://10.77.0.3:8082/ctl?ttl=0&reset=1&mode=public'`.
6. Negative control 1 — direct loopback is rejected: `POST /llmchat/connect` with `server.url=http://127.0.0.1:19000/mcp` → `400 {"detail":"Invalid server URL"}`.

8. PoC — reset with TTL 0 and rebind mode: `curl 'http://10.77.0.3:8082/ctl?ttl=0&reset=1&mode=rebind'`, then `POST /llmchat/connect` with `server.url=http://rebind.test:19000/mcp` → `200`, `tools:["internal_only_secret_tool_7f3a"]`.

#### Impact
Any authenticated user holding the default `developer` role (or any role granted `llm.invoke`) can make the gateway open connections to loopback/RFC1918 services. Demonstrated: enumerating and invoking a tool on an internal-only MCP server, with the tool's output returned to the user. Realistic consequences: access to internal admin APIs, metadata services, databases and sidecars reachable from the gateway host, and execution of any write-capable tool exposed by those internal servers. Scale: every deployment that enables `llmchat` and grants `llm.invoke` to non-admin roles — the default bootstrap grants it to `developer` and `team_admin`.

#### Affected Demographic
Deployments of mcp-context-forge 1.1.1 with `LLMCHAT_ENABLED=true` and a reachable internal MCP/HTTP service on the gateway host or its private network; users with `developer`, `team_admin`, or any custom role carrying `llm.invoke`.

#### Recommended Fix
- **Status: fixed upstream.** Commit `a1c3293b4657140cd801ecc4873a96919ed7dd95` (PR #7658) resolves and pins the outbound target (`resolve_pinned_target` + `build_pinned_httpx_client_factory`, `SniPinningTransport`, `follow_redirects=False`) and shipped in **v1.1.2** on 2026-11-25. Verified in the 1.1.2 sdist (sha256 `4c7248d17ea73f6d5f5443b943aab2386f09afdffc5d8da02e5ebafb45aa213c`), `mcpgateway/services/mcp_client_chat_service.py:2177,2180`. The guidance below is retained as design rationale.
- **Primary:** in `llmchat_router.connect`, replace the bare `validate_url` with the existing `validate_url_for_connection_pinning` / `resolve_pinned_target` flow and pass the **pinned IP** into the transport (Host header and TLS SNI preserved). Do not let the transport re-resolve.
- **Quick mitigation:** deny `127.0.0.0/8`, `::1`, `169.254.0.0/16`, and RFC1918 at socket-connect time inside the MCP transport, not only at URL validation.
- **Defence in depth:** re-validate the peer address after connect; require an admin-managed server allowlist for `/llmchat/connect`; restrict `llm.invoke` to explicitly trusted roles; log the resolved peer IP with every connect.

### 5.3 Falsified / refuted items and corrections
- **Refuted — direct loopback SSRF:** `server.url=http://127.0.0.1:19000/mcp` → `400 Invalid server URL`. Validation blocks literal loopback; only rebinding works.
- **Refuted — cached public answer:** with `ttl=300` and a warm cache, connect → `500 Service initialization failed`, 0 internal tool calls. Confirms the attack depends on TTL 0 (or cache expiry) and that the resolver path is the pivot.
- **Refuted — attacker-side network reachability:** `atk` cannot reach `10.77.0.2:19000` or its own `127.0.0.1:19000` (connection refused). The internal tool is reachable only through the gateway, proving the request originates from the target.
- **Refuted — admin-only exploitation:** the PoC runs as `dev@example.com` with only the default `developer` role; no admin permission is required at exploit time.
- **Correction note (auth model):** earlier draft assumed `developer` was a global role. It is **team-scoped**; the working assignment is `{"role_id": <developer id>, "scope": "team", "scope_id": <team id>}`. `scope: "global"` returns `400 Invalid request`.
- **Correction note (provider `api_base`):** earlier draft used a literal public IP alias (`93.184.216.34`) plus `ip addr/route`, which failed because the base image has no `ip` binary. Final PoC uses `api_base=http://rebind.test:8081/v1` with the LLM stub on the gateway loopback; the DNS control plane switches between `public` (provisioning) and `rebind` (exploitation) modes.
- **Correction note (paths/commit):** report now uses `/home/teycir` paths and pins the tested commit `85474a7c0eefc8c5d0e958400af7bc0ce59dfe63`; the previously cited `ff07553d…` was not present in the local clone.
- **Fix verification (2026-11-25):** `a1c3293b4657140cd801ecc4873a96919ed7dd95` is an ancestor of `v1.1.2` (`compare` → `ahead_by: 2`, `behind_by: 0`).
